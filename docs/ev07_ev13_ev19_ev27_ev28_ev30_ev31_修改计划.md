## 二、场景与根因分析

### 2.1 ev07：首轮从「抱怨」中抽取偏好并调用工具

- **场景**：用户首轮说「唉，我现在的房子住得不太舒服，采光不好，房间也小」，后续多轮才说「想换个房子」「想要两居室，预算4000以内…」「这套不错，我可以租吗？」。
- **用例期望**：Round 1 即调用 `update_preferences`，且 `contains` 包含 `orientation: "朝南"`、`min_area: 80`（从「采光不好」→ 朝南、「房间也小」→ 面积偏好 推断）。
- **当前行为**：Agent 的 system prompt 明确写「单纯抱怨、吐槽当前住房（如采光不好、房间小、太吵）且**未表达找房意图**时 → **只做共情回复，不调用任何工具**」。因此首轮仅共情，未调工具。
- **根因**：产品/用例期望是「首轮就从抱怨中推断偏好并写入 update_preferences」，与当前 prompt 的「仅在有找房意图时才调工具」策略冲突。

**修改计划（二选一或组合）**  
1. **改 Agent**：在 system prompt 中增加一条策略——若用户首轮仅抱怨住房问题（采光/面积/噪音等），可**可选**地在本轮调用 `update_preferences` 仅写入可推断的软偏好（如 orientation、min_area、noise_preference），并说明「后续用户一旦说找房再 search」；并保留「未表达找房意图时不调用 search_by_preferences」的约束。  
2. **改用例**：若产品接受「首轮只共情」，则 ev07 的 Round 1 的 `tool_call_args` 改为可选或删除，或改为不校验工具调用、只校验回复非空。

---

### 2.2 ev13：第二轮「放宽预算」时需携带上一轮的不变条件

- **场景**：Round 1「帮我找朝阳区两居室，预算6000以内」→ update_preferences + search；Round 2「预算放宽到8000看看」→ 仅变更 max_price。
- **用例期望**：Round 2 的 `update_preferences` 调用中 `contains` 包含 `location: ["朝阳区"]`、`bedrooms: "2"`、`max_price: 8000`。
- **当前行为**：Agent 遵循「每轮 update_preferences 只提取**本轮新增或变更**的偏好字段」，故 Round 2 只传了 `max_price: 8000`。后端 `tools.update_preferences` 会合并 session 内已有偏好，搜索结果是正确的，但**断言**检查的是当次调用的 **args**，要求与 contains 完全一致，导致报缺参数。
- **根因**：断言要求「当次调用的参数集」必须包含 location、bedrooms；Agent 行为是「只传变更项，依赖 session 合并」。

**修改计划（二选一或组合）**  
1. **改 Agent**：在 system prompt 中明确——在「仅放宽/收紧部分条件」（如只改预算、只改区域）的多轮场景下，调用 `update_preferences` 时需**显式传入本轮的变更 + 上一轮与结果仍相关的不变条件**（如 location、bedrooms），以便当次调用参数完整，满足评测对「当次 args」的校验。  
2. **改用例/断言**：ev13 Round 2 的 `contains` 只保留 `max_price: 8000`；或断言引擎支持「仅校验 contains 中列出的键，实际 args 允许多传其他键」，这样 Agent 只传 max_price 也能通过。

---

### 2.3 ev19：Round 3「那套可以租吗？」期望先 get_house_detail 再租

- **场景**：Round 2 用户问「便宜那套离地铁多远？」→ 期望 get_house_detail(HF_277)；Round 3「那套可以租吗？」。
- **用例期望**：Round 3 调用 `get_house_detail`（house_id: HF_277），不要求本轮必须 execute_action。
- **当前行为**：Agent 将「那套可以租吗？」直接理解为租房意图，调用了 `execute_action`，未先调用 `get_house_detail`。
- **根因**：用例设计为「先查详情再租」的流程；Agent 选择了更短路径「直接租」。

**修改计划（二选一或组合）**  
1. **改 Agent**：在 system prompt 中约定——当用户在前一轮刚问过某套房（如距离/详情），下一轮说「这套/那套可以租吗？」时，**先**调用 `get_house_detail` 确认房源与状态，再视情况调用 `execute_action`；或明确「可以租吗」在评测场景下优先解析为「先查详情再租」。  
2. **改用例**：若产品接受「直接租」也为正确，则 Round 3 的 expect 改为接受 `get_house_detail` 或 `execute_action` 任一（例如用多分支 expect 或放宽 tool_call_args）。

---

### 2.4 ev27：传入 `available_before` 导致断言「未声明参数」失败

- **场景**：用户说「帮我找3月份可以入住的房子，海淀区两居室」。
- **用例期望**：`update_preferences` 的 `contains` 仅声明 `location: ["海淀"]`、`bedrooms: "2"`。
- **当前行为**：Agent 正确解析了「3月份可以入住」，并传入了 `available_before`（或等价字段），同时传了 location、bedrooms。`tools.py` 和 API 支持 `available_before`，行为正确。
- **根因**：断言引擎 `_tool_call_args` 要求**实际 args 的键集合与 contains 的键集合完全一致**，不允许「未在 contains 中声明的参数」。因此多传了 `available_before` 即报错。

**修改计划（二选一或组合）**  
1. **改用例**：ev27 的 `contains` 中增加 `available_before` 的期望（例如 `available_before: "3月"` 或与 mock 一致的取值），使实际调用与 contains 一致。  
2. **改断言引擎**：支持「contains 为必含键集合，实际 args 允许包含更多键」（allow_extra_keys），这样 Agent 多传 `available_before` 不判失败。  
3. **改 Agent**（不推荐）：在仅需满足当前用例时，可要求「当用户只提区域+户型时不要传 available_before」——会损失语义，不推荐作为主方案。

### 2.5 ev28：传入 `location` 导致断言「未声明参数」失败

- **场景**：用户说「我在西二旗上班，想找通勤30分钟以内的房子」。
- **用例期望**：`update_preferences` 的 `contains` 仅声明 `max_commute_minutes: 30`。
- **当前行为**：Agent 合理地将「西二旗上班」解析为位置/通勤起点，可能传了 `location`（如西二旗）和 `max_commute_minutes: 30`。通勤筛选在 API 层是西二旗相关，行为合理。
- **根因**：同 ev27，断言要求 args 的键与 contains 完全一致，多传 `location` 即报错。

**修改计划（二选一或组合）**  
1. **改用例**：ev28 的 `contains` 中增加 `location` 的期望（如 `location: ["西二旗"]` 或与 Agent 实际传值一致），使键集一致。  
2. **改断言引擎**：同上，支持 allow_extra_keys，只校验 contains 中列出的键。  
3. **改 Agent**（不推荐）：仅传 max_commute_minutes、不传 location——可能削弱「西二旗通勤」的语义，不推荐作为主方案。

- **根因**：与 ev07 相同——prompt 约定「未表达找房意图时不调工具」，而用例期望首轮就抽取噪音偏好并写入 update_preferences。

## 三、断言引擎与用例约定（归纳）

- **当前断言**（`runner._tool_call_args`）：  
  - 实际某次工具调用的 `args` 的**键集合**必须与用例中 `contains` 的**键集合完全一致**；  
  - 多传键 → 「存在未在 contains 中声明的参数」；少传键 → 「缺少参数」。  
- **影响**：  
  - Agent 合理多传（如 ev27 的 available_before、ev28 的 location）会判失败；  
  - Agent 合理少传（如 ev13 只传 max_price、依赖 session 合并）也会判失败。

因此修改计划中同时包含「改 Agent 以贴合当前断言」与「改用例/断言以更符合语义」两类选项。

## 四、推荐修改优先级（仅计划，不实现）

1. **断言引擎**  
   - 增加「仅校验 contains 中列出的键，实际 args 允许包含更多键」的策略（可按用例配置，如 `strict_tool_args: false`）。  
   - 这样 ev27、ev28 无需改 Agent 或改 contains 即可通过；ev13 若用例只写 max_price，也可通过。

2. **用例**  
   - ev27：在 `contains` 中增加 `available_before`（或采用上述宽松断言）。  
   - ev28：在 `contains` 中增加 `location`，或采用宽松断言。  
   - ev13：Round 2 的 `contains` 仅保留 `max_price: 8000`，或采用宽松断言。

3. **Agent system prompt**  
   - **ev07 / ev30**：增加「首轮仅抱怨时，可选择性调用 update_preferences 写入可推断的软偏好（如 orientation、min_area、noise_preference），且不调用 search，直到用户表达找房意图」。  
   - **ev13**：若保持严格断言（必须显式传 location、bedrooms），则增加「部分条件变更时，显式携带上一轮不变条件」。

4. **用例 ev19**  
   - 若产品接受「直接租」：Round 3 改为接受 `get_house_detail` 或 `execute_action`，避免单一路径过于严格。
