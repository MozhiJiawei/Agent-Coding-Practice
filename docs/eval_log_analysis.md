# 评测日志失分分析（EV-002 多轮用例）

## 一、规则依据（来自 docs/task.md、interface.md）

| 规则 | 内容 |
|------|------|
| **计分** | 单轮/多轮任务按「给出的答案与用例答案匹配的数量」给分，匹配越多得分越高。 |
| **输出格式** | 房源查询完成后 `response` 必须为**合法 JSON 字符串**，包含 `message` 和 `houses`；**不能包含自然语言前缀**。 |
| **时间约束** | 执行单个用例「从任务下发到响应最终答案时间 **减去 模型调用时间**」不能超过 **5 秒**，超过则**当前用例任务执行失败**。 |

## 三、可能失分原因

### 1. 答案命中不足（最可能）

- 判题用「标准答案」里的房源 ID 集合与 Agent 最终返回的 `houses` 做匹配（通常为集合交集或子集）。
- 若标准答案与第 3 轮的 5 个 ID 不一致（例如判题期望「仅线上 VR 看房」为硬约束，只接受部分房源；或排序/筛选逻辑与平台数据不一致），则命中数不足，按比例扣分。

**建议**：若有公开/样例答案或平台给出该用例的期望 houses，可用 `scripts/analyze_eval_log.py` 或自写脚本对比「最后一轮 houses」与期望集合，计算命中数与占比。

### 2. 5 秒规则导致用例判失败

- 规则：**总耗时（任务下发到最终响应）− 模型调用时间 > 5 秒** → 该用例**执行失败**（0 分）。
- 日志中每轮 duration_ms 约 66s、79s、79s，为**含模型调用**的单轮总耗时；判题会减去所有模型调用时间，若剩余时间 > 5s 即失败。
- 若 Agent 在工具调用、序列化、网络等非模型部分耗时过长，可能触发此条。

**建议**：在日志或平台中区分「模型调用总耗时」与「其他逻辑耗时」，确保「其他逻辑耗时」< 5s。

### 3. 其他

- **response 格式**：当前日志中各轮 response 均为合法 JSON、含 message 与 houses、且以 `{` 开头，无自然语言前缀，此项未见违规。
- **status**：各轮均为 `success`，无异常。

## 四、脚本使用

```bash
# 分析默认日志 restored/eval_l00933108_EV-002-0_1772635308097670897.jsonl
python scripts/analyze_eval_log.py

# 指定其它 jsonl 日志
python scripts/analyze_eval_log.py path/to/other_eval.jsonl
```

脚本会：

- 解析每轮 USER_REQUEST / USER_RESPONSE；
- 校验 response 是否为合法 JSON、是否包含 message 与 houses、是否存在自然语言前缀；
- 提取每轮 houses 与 duration_ms；
- 输出规则提醒与可能失分点。

若后续有标准答案文件（例如 `expected_houses_EV-002.txt` 或 JSON），可在脚本中增加「最后一轮 houses 与标准答案集合求交集，输出命中数与命中率」的校验逻辑，便于量化失分原因。

## 五、基于交互与语义的失分推断（无标准答案时）

在**没有正确结果**的前提下，从对话语义和第三轮搜索/返回内容可以推断以下**最可能的失分原因**。

### 1. 看房方式：软约束导致混入「线下+线上」房源（最可能）

- **用户原话（第 3 轮）**：「希望能线上VR看房，**不用跑现场**」
- **当前行为**：Agent 将「希望」理解为软偏好，调用了 `viewing_method: "仅线上VR看房", viewing_method_is_soft: true`。搜索端按软约束处理，**不排除**「线下+线上」房源，只对「仅线上VR看房」加分。
- **实际返回的 5 套中**：
  - **HF_3265 锦绣锦园2区** 的 tags 为 **「线下+线上」**，并非「仅线上VR看房」。
  - 其余 4 套（HF_2611、HF_6535、HF_625、HF_9703）均为「仅线上VR看房」。
- **语义冲突**：「不用跑现场」明确表示不想到场，若判题按**硬约束**理解——最终答案只允许「仅线上VR看房」——则 HF_3265 属于**错误命中**，会直接导致扣分（例如 5 套中 1 套错误，按命中数计分时少 1 个正确 ID）。

**结论**：当用户同时说「希望线上VR看房」和「不用跑现场」时，更合理的语义是**仅接受线上看房**，应把 `viewing_method` 设为硬约束（不设 `viewing_method_is_soft`），这样搜索会排除「线下+线上」，最终 Top5 全为「仅线上VR看房」，与判题预期更一致。

### 2. 装修与地铁为软约束，Top5 与「理想排序」可能不一致

- **装修**：用户第 1 轮说「最好精装修」→ 已正确设为 `decoration_is_soft: true`。但第 3 轮返回中 **HF_625 为空房、HF_9703 为简装**，若判题期望「在满足硬约束前提下尽量优先进精装」，则我们的排序（按当前 soft_score）可能与标准答案的 5 个 ID 不完全一致，导致命中数减少。
- **近地铁**：用户要求「近地铁交通方便」且设为软约束，第 3 轮中有多套距地铁 4km+（HF_6535、HF_625、HF_3265）。若判题答案更偏向「近地铁」的 5 套，我们的集合会与之有差异。

这两点属于**排序/筛选优先级**差异，在无标准答案时无法定量，但可作为次要失分来源。

### 3. 建议的代码/策略调整（针对推断 1）

- **System prompt 或意图规则**：约定当用户表达「线上VR看房」且带有**明确拒绝线下**的表述（如「不用跑现场」「不想跑现场」「不想到场」）时，将 `viewing_method: "仅线上VR看房"` 视为**硬约束**（不传或传 `viewing_method_is_soft: false`），这样 `search_by_preferences` 会过滤掉「线下+线上」房源，最终返回的 5 套全部为「仅线上VR看房」，减少因 HF_3265 这类房源导致的失分。
